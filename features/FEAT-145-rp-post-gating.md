# FEAT-145 — РП-гейт действий через намерение поста

**Status:** CONCEPT (обсуждён с заказчиком, готов к разбивке на задачи)
**Связанные фичи:** [[FEAT-144-party-system]] (стык в «групповой атаке» и активностях отряда).

---

## 1. Проблема и цель

Игра ролевая, но автоматизация уводит от РП: игрок приходит на локацию с 10 волками, пишет **один минимальный постик** и просто вырезает всех мобов, если хватает ресурсов. Нет отыгрыша событий.

**Цель:** привязать действия на локации к **намерению в посте**. Действие (напасть, добыть, войти в данж, PvP, **поговорить с НПС**) становится доступным только после **квалифицирующего поста**, который декларирует, на что он направлен. Отыгрыш качества — за админами (пост-фактум), система обеспечивает лишь минимальный барьер.

---

## 2. Механика в двух словах

1. У поста появляется **намерение (`post_type`)** и, для боя/PvP, **список целей**.
2. Квалифицирующий (не-обычный) пост требует **≥ 500 символов** (выше общего мин. 300).
3. Пост создаёт **гейт-токены** (`action_gates`) — «право совершить действие X по цели Y».
4. Кнопка действия (`Напасть` / `Добыть` / `Войти` / `Поговорить`) доступна, **только если есть открытый гейт** под эту цель. Флоу действия перед запуском **спрашивает** locations-service и **гасит** гейт.

---

## 3. Гейтируемые действия и правила

| Действие | Мин. символов | Цели | Гейт |
|---|---|---|---|
| **Бой с мобами** | 500 | ⌊символы/200⌋ мобов, выбираешь в конце поста | по одному на выбранного моба |
| **PvP** (обоюдный/жёсткий) | 500 | цель-игрок | 1 (+ admin-approve для жёсткого, §7) |
| **Сбор** | 500 | узел добычи | 1 на узел |
| **Данж** (вход) | 500 | данж | 1 |
| **Диалог с НПС** | 500 | НПС | 1 на НПС |
| Обычный пост (рп) | 300 (как сейчас) | — | — |

**Боевой пример:** локация с 5 мобами → пишешь пост на 1000 символов → в конце выбираешь до ⌊1000/200⌋ = 5 целей → отправил → все 5 мобов стали атакуемыми. Убил — пишешь следующий пост под оставшихся.

**Абуз** («пост рп-путём не про мобов, а цели выбраны») ловят **админы** — система не проверяет смысловое соответствие, только длину и факт выбора целей.

---

## 4. Модель данных (locations-service, владелец постов)

Существующее: `posts` (id, character_id, location_id, content, created_at — `models.py:152`), мин. длина `MIN_POST_LENGTH=300` (`crud.py:20`), длина = `len(strip_html_tags(content))` (`crud.py:23`), создание `POST /locations/posts/` (`main.py:609`).

**Добавить:**
```
posts.post_type   ENUM(regular, combat, pvp, gathering, dungeon, npc_dialogue) DEFAULT regular

action_gates
  id             BIGINT PK
  character_id   INT
  location_id    BIGINT FK -> Locations.id
  post_id        INT FK -> posts.id
  action_type    ENUM(combat, pvp, gathering, dungeon, npc_dialogue)
  target_ref     INT NULL          -- mob character_id / player character_id / node_id / dungeon_id / npc_id
  status         ENUM(open, consumed, expired) DEFAULT open
  created_at     TIMESTAMP
  consumed_at    TIMESTAMP NULL
  INDEX(character_id, location_id, action_type, status)
```

Константы: `MIN_ACTION_POST_LENGTH = 500`, `SYMBOLS_PER_COMBAT_TARGET = 200`.

При создании поста с `post_type != regular`:
- проверить длину ≥ 500;
- для `combat`: число выбранных целей ≤ ⌊длина/200⌋ → создать N `action_gates(open)`;
- для остальных: 1 гейт под цель.

---

## 5. Consumption (гашение гейта)

- **Бой:** гейт `combat` под цель гасится в момент **старта боя** против этой цели (перед `POST /battles/`). Пережил бой моб или нет — процедуру под него повторяешь новым постом (гейт уже потрачен на инициацию).
- **Сбор/данж/НПС:** гейт гасится при запуске соответствующего действия.
- **Срок жизни:** гейт живёт, пока игрок на этой локации; **сгорает (`expired`) ТОЛЬКО при уходе с локации** — по времени не истекает (решено).

---

## 6. Групповой стык (с [[FEAT-144-party-system]])

- При атаке **группой** боевой пост пишет **только инициатор** (лидер или подтвердивший групповой бой) — он объявляет стычку за отряд; участники просто присоединяются, свой пост не пишут («не душно»).
- Гейт создаётся на инициатора; сборка группового боя (FEAT-144 §6.1) проверяет гейт инициатора.

---

## 7. PvP: обоюдный vs жёсткий

**Обоюдный (по согласию):**
- Оба лидера/игрока пишут PvP-посты друг на друга (условия дуэли: встретились, поговорили, договорились).
- Система проверяет наличие обоюдных гейтов → бой стартует. **Админы следят пост-фактум** за качеством отыгрыша.

**Жёсткий (без согласия второй стороны):**
- Инициатор пишет PvP-пост с целью → создаётся **запрос на админ-одобрение** «ПвП Нападение».
- **В модалку боя никто не попадёт, пока админ не одобрит.**
- Переиспользуем скелет **admin join-request** (battle-service): таблица `battle_join_requests` (`models.py:176`), паттерн pending→approve/reject с пермишеном `battles:manage`, WS-уведомления, пауза (`main.py:3474/3252/3407`). Аналогично заводим `pvp_attack_requests` (или расширяем существующий) + админ-эндпоинты approve/reject; на approve → создаётся бой (`POST /battles/`).
- Уже есть частичный `POST /pvp/attack` (`main.py:2608`), блокируется на `marker_type=='safe'`. Новый слой поверх: требовать пост + админ-одобрение.

## 8. Эндпоинты / интеграции

**locations-service (владелец гейтов):**
```
POST /locations/posts/            -- расширить: post_type + targets; при не-regular проверять 500 и создавать action_gates
GET  /locations/internal/action-gate    -- {character_id, location_id, action_type, target_ref} -> {open: bool}
POST /locations/internal/action-gate/consume  -- гасит гейт (service-to-service)
```

**Кто проверяет/гасит гейт перед действием:**
- **Бой с мобом:** battle-service `create_battle_endpoint` (`main.py:627`) перед созданием боя → проверить+погасить `combat`-гейт инициатора.
- **PvP:** battle-service `/pvp/attack` / вызов — проверка гейта(ов); жёсткий → admin-approve (§7).
- **Сбор:** locations-service `POST /.../gathering-nodes/{node}/start` (`main.py:3135`) — гасит `gathering`-гейт (внутри одного сервиса, проще).
- **Данж:** dungeon-service `enter` — проверка `dungeon`-гейта.
- **НПС-диалог:** эндпоинт запуска диалога — проверка `npc_dialogue`-гейта.

---

## 9. Фронт

- **Редактор поста:** селектор намерения (`Обычный / Боевой / PvP / Сбор / Данж / Диалог с НПС`); для боевого/PvP — **выбор целей в конце поста** (мобы/игроки, присутствующие на локации), лимит целей = ⌊символы/200⌋, живой счётчик. Валидация 500 символов для не-обычных.
- **Кнопки действий** (`Напасть` на мобе, `Поговорить` с НПС, `Добыть`, `Войти`) — **disabled + подсказка** «нужен боевой пост / пост-намерение», пока нет открытого гейта.
- Мин. длину и подсчёт символов — переиспользовать существующий счётчик редактора.

---

## 10. Фазовый план

- **Ф1.** `post_type` + `action_gates` + расширение создания поста (500-гейт, цели по 200). Редактор: намерение + выбор целей.
- **Ф2.** Гейт боя с мобами (проверка+гашение в battle-service) + disabled-кнопка на фронте.
- **Ф3.** Сбор + данж + **диалог с НПС** под гейт.
- **Ф4.** PvP: обоюдный (двусторонние гейты) и жёсткий (admin-approve, §7).
- **Ф5.** Стык с отрядом (инициатор пишет за группу) — синхронно с FEAT-144 Ф3/Ф4.

## 11. Решённые / открытые вопросы

- ✅ **TTL/уход с локации:** гейт сгорает **только при уходе** с локации, по времени не истекает.
- ✅ **Диалог с НПС:** механика диалога **уже есть**. Гейтим **открытие карточки/возможностей НПС** — как «Напасть» у мобов: без `npc_dialogue`-поста карточку НПС открыть нельзя.
- ✅ **Повторная атака недобитого моба:** да, нужен **новый пост** (гейт тратится на инициацию боя).
- **PvP-флаг локации** для жёсткого PvP — зависимость от будущей системы правил локаций (см. FEAT-144 §13); пока — только `marker_type=='safe'` блок.
