# FEAT-144 — Единая система отрядов (Party System)

**Status:** CONCEPT (обсуждён с заказчиком, готов к разбивке на задачи)
**Связанные фичи:** [[FEAT-145-rp-post-gating]] (стык в точке «групповая атака» и все действия-через-пост), FEAT-143 (групповые бои — источник `battle_parties`).

---

## 1. Обзор и цель

Сейчас в проекте **две параллельные, дублирующие друг друга системы группировки**, и обе одноразовые:

- **Боевая пати** — `battle_parties` / `battle_party_members` (battle-service, `models.py:217/243`): лидер, инвайты с принятием/отказом, команды (0/1), гейт по локации, TTL 2ч, разовая (стартанул бой → `started`).
- **Данжевая пати** — `dungeon_sessions` / `dungeon_session_members` (dungeon-service, `models.py:125/148`): сессия = пати, инвайт без принятия, макс 4, разовая на забег.

Плюс на голой локации **standing-группы нет вообще** — «кто здесь» считается по `characters.current_location_id`.

**Цель:** одна **постоянная** сущность «Отряд», живущая в **отдельном party-service**, из которой запускаются все групповые активности (бой с мобами, PvP, данж, сбор), с бонусами и социальным отображением на локации. Убирает дубль и ручную сборку врагов (враги — контентные или другая группа по вызову).

---

## 2. Ключевые решения (согласованы с заказчиком)

| Вопрос | Решение |
|---|---|
| Жизненный цикл | **Постоянный** отряд, не распадается никогда |
| Перемещение | **Раздельное**. Отряд НЕ рвётся при смене локации участником |
| Со-локация | Статус 🟢 (на локации активности) / 🔴 (в другом месте). В активностях и бонусах участвуют только 🟢 |
| Владелец | **Новый отдельный `party-service`** (заказчик планирует ещё фичи для отрядов) |
| Лимит | **4** (лидер + 3) |
| Создание | Стоит **активный опыт** (`active_experience`); пока порог **0** (для тестов). Лидер задаёт **имя** + **аватар** |
| Один отряд на игрока | Да (участник состоит максимум в одном отряде) |
| Инвайт | Только когда лидер **на одной локации** с приглашаемым (рп-отыгрыш). С **принятием/отказом** |
| PvP | Группа-vs-группа/соло по **вызову** (см. §6.3), не «зови врагов в своё лобби» |

## 3. Модель данных (party-service, новая БД-зона в общей MySQL)

Уникальный `version_table` для Alembic: `alembic_version_party`.

```
parties
  id              BIGINT PK
  name            VARCHAR(60)         -- имя отряда
  avatar          VARCHAR(255) NULL   -- S3-путь символа отряда
  leader_character_id  INT            -- лидер (cross-service, без FK)
  created_at      TIMESTAMP
  -- на будущее: settings JSON, level и т.п.

party_members
  id              BIGINT PK
  party_id        BIGINT FK -> parties.id (CASCADE)
  character_id    INT
  user_id         INT
  is_leader       BOOL
  status          ENUM(invited, accepted)   -- принятие/отказ как в battle_parties
  joined_at       TIMESTAMP
  UNIQUE(party_id, character_id)
  UNIQUE(character_id)   -- один отряд на игрока (только для accepted; см. §13)
```

XP-бонус (§5) — константа `PARTY_XP_BONUS_PCT = 10` в config party-service.
Стоимость создания — `PARTY_CREATE_COST_ACTIVE_XP = 0` (пока).

## 4. Со-локация 🟢 / 🔴

Вычисляется **в реалтайме**, не хранится: член 🟢 если его `characters.current_location_id` == локация активности (или, для отображения во вкладке, == локация смотрящего). party-service дергает character-service `GET /characters/by_location?location_id=` (`character-service/main.py:1456`) или точечно профиль.

- Для **активностей**: набор участников = accepted-члены, чей `current_location_id` == локация запуска.
- Для **вкладки/отображения**: 🟢/🔴 относительно локации смотрящего.

---

## 5. XP-бонус отряда (согласованная модель)

Константа **+10%** (`PARTY_XP_BONUS_PCT`).

- **A. Само-бонус +10%** на СВОЙ заработанный опыт (мобы, данж, посты) — **только если рядом ≥1 зелёный соотрядец**. Один на локации → бонусов нет.
- **B. Отлив соотрядцам:** боевой/данж-опыт члена отряда капает **каждому другому зелёному** +10% от него (пассивно, без участия). **Посты НЕ отливают** — только само-бонус пишущему.
- **C. Групповая активность:** в групповом бою/данже каждый зелёный участник берёт полную базу, и к ней применяется A.

Проверка (волк = 100 базы):

| Ситуация | Актор | Зелёные соотрядцы рядом |
|---|---|---|
| Убили **группой** | 110 | по 110 (участвовали) |
| Убил **соло** член отряда | 110 | по +10 (отлив, без базы) |
| **Пост** | +10% себе | ничего |

**Реализация:** опыт начисляется через `PUT /attributes/{id}/passive_experience` (character-attributes-service `main.py:760`). Каждый источник (бой/данж/пост) при начислении дёргает party-service `POST /internal/party/xp-bonus` с `{character_id, base_xp, source, location_id}`; party-service считает 🟢-состав и раздаёт бонусы/отлив тем же `passive_experience`-эндпоинтом.
Точки-источники: пост-опыт `locations-service/crud.py:44` (`award_post_xp_and_log`); мобы/данж — battle-service/dungeon-service в момент начисления опыта за бой.

## 6. Активности через отряд

### 6.1. Бой с мобами (группой/соло)
Стык с [[FEAT-145-rp-post-gating]] (боевой пост открывает цели) и со «стаями мобов» (§13).
- **Лидер** атакует моба → выбор **«группой»** (втягивает 🟢-участников как team 0) или **«соло»**.
- **Не-лидер** → «соло» сразу, либо **запрос лидеру** «бить группой» → лидер подтверждает → групповой бой.
- Сборка боя: party-service отдаёт 🟢-состав, battle-service `POST /battles/` (`main.py:627`) собирает `players` = team 0 (отряд) + team 1 (моб/стая). Никого «в враги» не зовём.

### 6.2. Данж и сбор
- **Данж:** заходит отряд; `dungeon_sessions` перестаёт быть «пати» и становится **раннраном, ссылающимся на `party_id`** (миграция §11). Состав = 🟢-участники на локации входа.
- **Сбор:** `gathering_nodes`/`gathering_sessions` (locations-service `models.py:491/560`). Если игрок в отряде — 🟢-участники встают на узел вместе; XP-бонус §5 применяется к добыче.

### 6.3. PvP — вызов
- Лидер шлёт **вызов** другому лидеру/соло-игроку. Обе стороны — свои отряды. Принятие → бой (team 0 отряд A, team 1 отряд B).
- **Обоюдный** бой: оба лидера пишут боевые посты ([[FEAT-145-rp-post-gating]] §6), админы следят пост-фактум.
- **Жёсткий/без согласия:** через **admin-approve** ([[FEAT-145-rp-post-gating]] §7, скелет `battle_join_requests`).

## 7. Отряд на локации (соц-отображение)

На странице локации другие игроки видят **какие отряды тут находятся**: имя, аватар-символ, и **каких участников видно на локации** (только 🟢; тех, кого нет — не показываем).

Реализация: `GET /party/by-location?location_id=` (party-service) → список отрядов с 🟢-составом (пересечение accepted-членов с `by_location`).

## 8. Эндпоинты party-service (порт — новый, напр. 8012; Nginx dev+prod, CI-матрица)

```
POST   /party                       -- создать (name, avatar, leader) — списывает active XP
GET    /party/mine                  -- мой отряд (состав, статусы 🟢/🔴)
POST   /party/{id}/invite           -- лидер зовёт (гейт: одна локация); создаёт member(invited)
POST   /party/{id}/respond          -- accept / decline
POST   /party/{id}/leave            -- выход; лидер-выход = передача/роспуск
DELETE /party/{id}                  -- лидер распускает
PATCH  /party/{id}                  -- настройки лидера (имя/аватар/…)
GET    /party/invites/incoming      -- мои входящие приглашения
GET    /party/by-location           -- §7, отряды на локации
POST   /internal/party/xp-bonus     -- §5, приём событий опыта (service-to-service)
GET    /internal/party/active-members -- 🟢-состав для сборки активности (для battle/dungeon/locations)
```

---

## 9. Интеграции (что дёргает party-service)

- **battle-service:** при сборке боя из отряда — берёт 🟢-состав; при начислении опыта за бой — шлёт `xp-bonus`.
- **dungeon-service:** сессия ссылается на `party_id`; при опыте — `xp-bonus`.
- **locations-service:** пост-опыт (`award_post_xp_and_log`) → `xp-bonus`; сбор — совместная постановка + бонус; `by-location` для §7.
- **character-attributes-service:** списание `active_experience` при создании; начисление бонусов `passive_experience`.

---

## 10. Профиль: вкладка «Отряд»

Видна **любому члену** отряда (не только лидеру). Показывает: имя+аватар, состав со статусами 🟢/🔴, входящие приглашения. **Настройки (имя/аватар/роспуск/кик) — только лидер.** Фронт: новый таб в `ProfilePage` (по образцу `PerksTab`).

---

## 11. Миграция со старых систем

- **`battle_parties`/`battle_party_members`** → выпилить лобби, заменить на «запуск боя из отряда». Существующие форминг-лобби просто истекают.
- **`dungeon_sessions`** → оставить как run-state, добавить `party_id`; членство берётся из отряда, а не пересобирается.
- Обе — отдельной фазой (Ф6), после того как party-service работает.

## 12. Фазовый план

- **Ф1. Костяк:** party-service + `parties`/`party_members`, создание (cost 0, имя, аватар), инвайт+принятие с гейтом локации, вкладка «Отряд», 🟢/🔴. Отряд просто существует.
- **Ф2. XP-бонус:** интеграция §5 со всеми источниками опыта.
- **Ф3. Активности:** данж от отряда, бой с мобами (группой/соло), совместный сбор.
- **Ф4. PvP группа-vs-группа** (вызов; жёсткий — admin-approve).
- **Ф5.** «Отряд на локации» §7 + профильные полировки.
- **Ф6. Миграция** старых `battle_parties`/`dungeon_sessions`.

*(«Стаи мобов» и «PvP-флаг локации» — отдельные зависимости, см. §13.)*

## 13. Открытые вопросы / зависимости

- **Стаи мобов** — отдельная фича: админ-раздел «Группы мобов» (мини-пати из ранее созданных мобов на локацию), атака по элементу = бой со всей стаей, индикатор состава («Стая волков ×4»). Нужна для §6.1 при бое отряда против нескольких мобов.
- **PvP-флаг локации** — placeholder на будущее (часть будущей системы «правил/событий локаций»). Сейчас есть частичный аналог: `POST /pvp/attack` блокируется на `marker_type=='safe'` (battle-service `main.py:2608`).
- ✅ **UNIQUE(character_id)** на `party_members` — ограничение только для **accepted** (в приглашённых можно висеть у нескольких отрядов; принять — только один).
- **Само-бонус при отсутствии 🟢** — подтверждено: один на локации = 0 бонусов.
- **Кик участника лидером** — добавить в §8 (`DELETE /party/{id}/members/{character_id}`), детали на Ф1.
